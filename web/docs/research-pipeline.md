# 자료조사 파이프라인

세모귀 웹앱의 AI 자료조사 구조와, 다음 단계(2단계) 확장 설계입니다. 코드: `app/research.py`, `app/ai_provider.py`, `app/jobs.py`, `app/research_library.py`.

## 1단계 (구현됨)

### 흐름 (고정 템플릿 작업 = 캐릭터·굿즈·콜라보·팝업 모두)

```
주제 입력 → (유형 자동이면) 유형 분류 (웹 없음)
 → [1] 자료 조사 research_only           웹 검색·페이지 읽기, 카드는 쓰지 않음
       (캐릭터 소개) 친구·가족 캐릭터별 추가 조사 1~2회
 → 서버 검증: 출처를 실제 조회 기록과 대조, 항목 상태·빈 이유·충분성·근거 기록
 → 조사 결과를 작업(job.research)에 먼저 저장  ← 화면에 바로 보이고, 구성안이 실패해도 남음
 → [2] 구성안 작성 compose_from_research  웹 도구 없음, 저장된 사실·출처만 사용
 → 카드 검사(글자 수·숫자·섞임) → 필요하면 다시 쓰기 1회 → 구성안 검토·수정·승인 (기존과 같음)
 → 보관함에 조사 버전 저장
```

- 구성안 작성이 실패·중단되면 **다시 시도**는 조사를 반복하지 않고 구성안만 다시 씁니다 (`researchStage`).
- 템플릿을 쓰지 않는 예전 형식 작업은 예전처럼 한 번의 호출로 조사와 구성안을 함께 만듭니다.
- AI 호출: 조사 1 + (캐릭터) 추가 조사 1~2 + 구성안 1 (+ 다시 쓰기 0~1). 구성안 단계가 따로 생긴 대신 조사 호출은 카드를 쓰지 않습니다.

### 조사 항목 정의 (`research.SPECS`)

유형마다 하나의 표에 항목을 정의합니다. 예전 이름(`ITEMS`, `CORE`, `ITEM_HINTS`)은 이 표에서 자동으로 만듭니다.

| 속성 | 뜻 |
| --- | --- |
| `official` | 공식 출처만 근거로 인정 (가격·일정 등) |
| `importance` | `core` 핵심(없으면 구성안을 쓰지 않음) / `high` 카드에 자주 쓰임 / `normal` |
| `core` | 핵심 그룹. 같은 그룹 중 하나만 확인돼도 됨 |
| `many` | 여러 개가 나열되는 항목 (라인업·친구 목록) → 충분성 평가 대상 |
| `volatile` | 시간이 지나면 바뀌는 정보 (가격·기간·운영 시간) |
| `hint` | 그 항목을 어디서 어떻게 찾는지 (특정 주제가 아닌 일반 안내) |

### 항목 상태

값이 있는 경우: `verified`(공식 확인) · `secondary`(2차 자료) · `image` · `user` · `listed`(검색 목록만, 확인 아님) · `unverified` · `conflict`.

값이 없는 경우, AI의 보고(`outcome`, `checkedUrls`)를 **실제 조회 기록**과 대조해 이유를 정합니다.

| 상태 | 화면 | 판단 근거 |
| --- | --- | --- |
| `not_found` | 자료 없음 | 항목을 확인하려고 읽은 페이지가 실제로 읽혔는데 정보가 없었음, 또는 검색 결과가 있었는데 찾지 못했다고 보고 |
| `failed` | 검색·읽기 실패 | 확인하려던 페이지 읽기가 실패(404·오류 등), 또는 검색 도구가 모두 실패 |
| `blocked` | 접근 제한 | 자동 접근 금지 사이트, 요청 대기 중인 사이트, 사이트가 거절(401·403·429·451·503) |
| `not_searched` | 미조사 | AI가 찾아보지 않았다고 답했거나 보고가 없음, 이번 조사에 검색·읽기 기록이 전혀 없음 |
| `missing` | 정보 확인 필요 | 예전 조사 기록 (이유가 기록되지 않음) |

- 조회 기록에 없는 주소는 근거로 삼지 않습니다 (AI가 "읽었다"고 해도).
- 실제 페이지 읽기가 있으면 '자료 없음'이 '실패·접근 제한'보다 우선합니다 (다른 곳에서 확인했으므로).

### 충분성 (`item.coverage`)

`many` 항목은 AI가 `complete`/`partial`/`unknown`과 이유를 적습니다. `partial`·`unknown`이면 **검토 필요**로 표시합니다. 인원수·개수를 강제하지 않고, 근거 없이 누락이라고 단정하지 않습니다. 값이 하나인 항목은 따지지 않습니다(`n/a`).

### 근거 기록 (`item.evidence`, `item.attempts`)

- `evidence`: 값마다 `{sourceId, url, title, kind, verification, pageRead, quote, quoteCheck, at}`
  - `pageRead`: 그 페이지를 실제로 읽었는지 (조회 기록 기준)
  - `quoteCheck`: 근거 문장이 페이지에 있는지 검증했는지. 1단계는 `not_checked`(검증하지 않음)만 씁니다.
- `attempts`: `{outcome, checked: [{url, result: read|failed|blocked|unknown}]}`

### 비교

`tools/compare_research.py A B` — 작업 id·보관함 버전 id·JSON 파일을 받아 조사 요약(검색 수, 읽은 출처, 공식 출처, 중요도별 확인 수, 상태별 개수, 검토 항목)과 항목별 상태를 나란히 보여 줍니다. `research.research_report()`가 요약을 만듭니다.

## 2단계 설계 (아직 구현하지 않음)

### A. 한국어·일본어·영어 검색어 계획

- 조사 전 **검색 계획** 호출 1회(웹 도구 없음, effort low, 약 $0.01~0.02): 주제의 별칭(한국판·원작·영문 이름), 공식 사이트 후보 도메인, 항목별 검색어(언어 표시)를 JSON으로 받습니다.
- 별칭·검색어는 사실로 쓰지 않습니다(카드·조사 항목에 넣지 않음). 조사 프롬프트에 "이 검색어를 우선 사용"으로만 전달합니다.
- 보관함 버전에 `plan: {aliases, queries}`로 저장해 다음 조사에서 재사용합니다.
- 연결 지점: `research_only()` 앞 단계, `SPECS[*].hint`와 `importance`로 항목 순서를 정함.

### B. 누락 항목 자동 재조사 (1회)

- 대상: 1차 조사 뒤 `importance`가 core·high이고 상태가 `not_found`·`not_searched`, 또는 `coverage.review`가 참인 항목.
- 제외: `blocked`(접근 제한, 대기 정책 존중), `failed` 중 같은 사이트가 대기 중인 경우.
- 1회만, 다른 언어·다른 검색어로(A의 계획 사용). 캐릭터 추가 조사(`_research_people`)의 2회차 방식을 일반화합니다.
- 병합 규칙: 이미 확인된 값(`verified`·`secondary`)은 고정. 새 값이 다르면 덮어쓰지 않고 `conflict`로 표시. 빈 항목만 채움.
- 연결 지점: `research_only()`에서 `_research_people` 다음, `_finish_research` 전. `attempts`에 회차(round)를 더합니다.

### C. 사용자가 고른 항목만 추가 조사

- 화면: 조사 항목 목록에 선택 상자 + "선택한 항목 다시 조사" 버튼 (AI 한도 차감 안내).
- API: `POST /api/jobs/{id}/research/items {keys: [...]}` → `_start_ai_task("research_items", ...)`.
- 실행: B와 같은 재조사 호출을 고른 항목만 대상으로. 결과는 조사 결과에만 반영하고, 그 항목을 쓰는 카드에는 "조사 결과가 바뀌었어요 · 이 카드 다시 쓰기" 안내만 표시합니다(자동으로 문구를 덮어쓰지 않음, 승인 해제 없음).
- 보관함: 새 버전(`parent` = 이전 버전 id, `delta` = 바뀐 항목)으로 추가합니다.

### D. 검증된 자료 유지 + 새 정보만 추가 (보강 조사)

- '새로 조사하기' 옆에 '보강 조사' 선택지: 이전 버전의 확인된 항목을 고정하고 빈 항목·검토 항목만 조사합니다(B와 같은 호출, 대상만 다름).
- `volatile` 항목(가격·기간 등)은 고정하지 않고 다시 확인합니다. 값이 바뀌면 `conflict`로 보여 사용자가 고르게 합니다.

### E. 근거 문장 검증 (선택)

- 기존의 정중한 접속기(`detail_images._Fetcher`: robots.txt 준수, 요청 간격, 대기 정책)로 출처 페이지를 한 번 받아 근거 문장이 본문에 있는지 확인해 `quoteCheck`를 `found`/`not_found`로 바꿉니다.
- Claude 사용량은 늘지 않지만 사이트 요청이 출처당 1회 늘어나므로, 금지·대기 중 사이트는 제외하고 버전당 1회만 합니다.

### 비용·시간 상한 (2단계에도 유지)

- 재조사는 자동 1회 + 사용자 요청 시에만. 호출당 `--max-budget-usd`, 시간 제한 유지. 필요하면 Claude CLI 최대 진행 횟수 옵션으로 반복을 막습니다.
- 접근 금지 사이트·요청 대기 사이트는 모든 단계에서 요청하지 않습니다.
